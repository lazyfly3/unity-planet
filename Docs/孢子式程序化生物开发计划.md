# 孢子式程序化生物开发计划

## 1. 文档目标

本文档用于指导当前 Unity 球形体素星球项目实现类似《孢子》（Spore）的程序化生物系统。

系统目标不是从一组完整生物预制体中随机选择，而是使用星球环境和稳定种子生成物种基因，再由基因生成身体结构、Mesh、骨架、外观、动画和行为。

核心流程：

```text
星球环境参数
    -> 生成物种基因
    -> 生成身体拓扑
    -> 生成 Mesh 和骨架
    -> 程序化步态与 IK
    -> 星球表面生成个体
    -> AI、生态与存档
```

《孢子》公开技术可以作为身体重建和动画适配的参考，但本项目的“根据星球环境自动产生物种”属于在该思路上的扩展。

参考资料：

- [Spore Creature Creator](https://www.ea.com/games/spore/spore-creature-creator)
- [Spore 程序化动画 SIGGRAPH 论文](https://chrishecker.com/Real-time_Motion_Retargeting_to_Highly_Varied_User-Created_Morphologies)
- [Spore 开发者技术回顾](https://chrishecker.com/My_Liner_Notes_for_Spore)

## 2. 第一版范围

第一版只实现以下能力：

- 只生成陆地生物。
- 支持两足、四足和六足形态。
- 每颗星球生成 3 个稳定物种。
- 每个物种同时出现不超过 10 个个体。
- 支持闲逛、进食、逃跑和追逐。
- 支持球面顶部、侧面和下半球移动。
- 支持物种与重要个体存档。
- 不实现飞行、游泳、繁殖和玩家生物编辑器。
- 不为每个物种制作完整生物预制体。

第一版完成条件：不同星球能稳定产生外观明显不同的生物，生物可以在任意球面方向正常站立和移动，离开星球后物种不会改变。

运行时允许创建程序化生物对象，因为任意数量和形态的生物无法全部预先放在场景层级中。固定管理器应手动存在于 `star` 场景层级，不使用完整生物预制体。

推荐层级：

```text
VoxelQuadSphereWorld
└── CreatureSystem
```

`CreatureSystem` 手动挂载 `PlanetCreatureSystem`，程序化个体作为它的运行时子对象。

## 4. 阶段一：建立数据模型

### 4.1 CreatureGenome

`CreatureGenome` 只保存生成身体所需参数，不保存 Mesh、Transform 或运行时组件。

建议字段：

```csharp
[Serializable]
public sealed class CreatureGenome
{
    public int seed;

    public int spineSegments;
    public float bodyLength;
    public float bodyRadius;
    public float bodyCurve;

    public int legPairs;
    public float legLength;
    public float legThickness;
    public float footSize;

    public float headSize;
    public int eyeCount;
    public int hornCount;
    public float tailLength;

    public CreatureLocomotion locomotion;
    public CreatureDiet diet;

    public Color primaryColor;
    public Color secondaryColor;
    public Color emissionColor;
    public float patternScale;
    public float roughness;
    public float emissionStrength;
}
```

### 4.2 CreatureSpeciesDefinition

物种定义保存整个物种共享的数据：

```csharp
[Serializable]
public sealed class CreatureSpeciesDefinition
{
    public string speciesId;
    public string displayName;
    public CreatureGenome genome;

    public float minimumScale;
    public float maximumScale;
    public int targetPopulation;

    public float aggression;
    public float curiosity;
    public float sociality;
}
```

### 4.3 CreatureInstanceState

个体状态只保存需要长期存在的数据：

```csharp
[Serializable]
public sealed class CreatureInstanceState
{
    public string instanceId;
    public string speciesId;
    public Vector3 localPosition;
    public Quaternion localRotation;
    public float age;
    public float health;
    public bool dead;
}
```

### 验收标准

- 可以创建一份测试基因。
- 可以序列化为 JSON 并正确恢复。
- 数据类型不直接引用运行时 GameObject、Mesh 或 Material 实例。

## 5. 阶段二：把生态特征固化到星球

当前 `ProceduralGalaxyGenerator` 已经计算温度、湿度、地质、大气和晶体活性。新增 `PlanetEcologySettings`，保留这些基础特征：

```csharp
[Serializable]
public sealed class PlanetEcologySettings
{
    public float temperature;
    public float moisture;
    public float gravity;
    public float atmosphere;
    public float geology;
    public float crystalActivity;
    public int speciesCount;
    public int creatureDensity;
}
```

需要修改：

- `GalaxyPlanetDefinition` 增加 `ecology`。
- `GalaxyGeneratedPlanetRecord` 增加 `ecology`。
- `ProceduralGalaxyGenerator.GeneratePlanet` 生成生态参数。
- 星球 `definition.json` 固化生态参数。
- 旧版固定星球提供手动默认生态参数。

星球首次进入后必须固化这些参数。以后修改生成算法时，已经访问过的星球不能改变生态和物种。

### 验收标准

- 相同世界种子和坐标得到相同生态参数。
- 不同生态星球的参数有明显差异。
- 离开星球并返回后参数完全一致。

## 6. 阶段三：确定性生成物种

新增 `CreatureSpeciesGenerator`。

输入：

```text
planet.seed
planet.ecology
speciesIndex
creatureGeneratorVersion
```

输出：

```text
CreatureSpeciesDefinition
```

物种种子必须通过稳定哈希生成：

```text
speciesSeed = StableHash(planetSeed, speciesIndex, generatorVersion)
```

不要使用字符串的运行时 `GetHashCode()`。优先复用无限星图已有的稳定 64 位哈希和 `StableRandom`。

### 环境约束

高重力星球：

- 身体低矮。
- 腿短而粗。
- 大型生物移动较慢。

高湿度星球：

- 身体更圆润。
- 更容易出现群居物种。
- 颜色偏青绿或高饱和冷色。

高温、高地质活动星球：

- 外壳更厚。
- 红黑配色概率增加。
- 可以出现发光裂纹。

高晶体活性星球：

- 晶角和晶体背板增加。
- 发光色与星球主色形成对比。

低大气星球：

- 身体更低矮。
- 不生成大型飞行结构。
- 感知器官数量受到限制。

随机值必须经过约束，不能让所有字段独立随机。每颗星球应先生成统一的“生物设计语言”，再生成多个具有共同特征的物种。

### 验收标准

- 同一个星球重复生成 100 次，物种定义完全一致。
- 不同星球的物种外观参数明显不同。
- 不生成零长度肢体、负尺寸或超出上限的节点。

## 7. 阶段四：生成身体拓扑

新增 `CreatureBodyGraph` 和 `CreatureBodyGraphBuilder`。

基因先转换为结构图，不直接生成 Mesh：

```text
Root
└── Spine0
    └── Spine1
        ├── Head
        ├── LeftFrontLeg
        ├── RightFrontLeg
        ├── LeftBackLeg
        ├── RightBackLeg
        └── Tail
```

节点结构：

```csharp
public struct CreatureBodyNode
{
    public int parentIndex;
    public Vector3 localPosition;
    public Quaternion localRotation;
    public float radius;
    public CreatureNodeType type;
}
```

必须满足：

- 腿左右成对。
- 腿连接在身体下侧。
- 前后肢体之间有最小距离。
- 头连接脊柱首端，尾巴连接末端。
- 身体尺寸与腿部尺寸保持合理比例。
- 最大节点数限制为 64 左右。
- 任意节点的父节点必须存在。

### 验收标准

- 使用 Gizmos 显示节点、半径和骨骼连接。
- 连续生成 1000 个身体结构，没有断链或异常值。

## 8. 阶段五：生成第一版 Mesh

第一版使用管状 Mesh，不直接实现高成本 Metaball：

1. 沿脊柱和肢体建立圆形截面。
2. 每个截面使用 8 或 12 个顶点。
3. 连接相邻截面。
4. 头部使用程序化球体或椭球。
5. 眼睛、脚和角使用简单程序化几何体。
6. 重新计算法线和包围盒。

同一物种共享生成结果：

```csharp
Dictionary<string, GeneratedCreatureAssets> speciesCache;
```

共享内容：

- Mesh。
- 骨架结构描述。
- 材质。
- 步态配置。

每只个体通过 `MaterialPropertyBlock` 设置细微颜色差异，不能为每个个体复制 Material。

后续高级版本可替换为：

```text
身体节点 -> SDF/Metaball -> Marching Cubes -> 连续身体 Mesh
```

### 验收标准

- 同一物种的所有个体共享一份 Mesh。
- 正反面、法线和包围盒正确。
- 肢体没有明显断裂或顶点连接错误。

## 9. 阶段六：自动骨架与蒙皮

新增 `CreatureRigBuilder` 和 `CreatureSkinningBuilder`。

每个身体节点生成骨骼。腿部统一使用语义名称：

```text
UpperLeg
LowerLeg
Foot
```

顶点权重根据骨骼距离计算：

- 最近骨骼获得主要权重。
- 父骨骼获得次要权重。
- 每个顶点最多受 2 到 4 根骨骼影响。
- 所有权重之和必须归一化。

动画系统不依赖具体骨骼名称，而是依赖肢体语义、左右侧、肢体组编号和足端位置。

### 验收标准

- 手动旋转任何骨骼时 Mesh 正确变形。
- 不出现顶点被拉到世界原点。
- 两足、四足和六足使用同一套骨架生成流程。

## 10. 阶段七：球面程序化行走

新增 `CreatureMotor`、`CreatureGaitController` 和 `CreatureFootIK`。

所有方向都必须根据星球中心计算：

```csharp
Vector3 radialUp =
    (transform.position - planetCenter).normalized;

Vector3 gravityDirection = -radialUp;

Vector3 tangentForward =
    Vector3.ProjectOnPlane(desiredDirection, radialUp).normalized;
```

禁止使用世界 `Vector3.up`、世界 Y 高度或只修改 X/Z 坐标。

每只脚的处理流程：

1. 计算理想落脚位置。
2. 从星球外侧向中心方向射线检测。
3. 获得真实地面点与法线。
4. 按抬脚曲线移动足端目标。
5. 使用 Two Bone IK 调整腿部。
6. 根据支撑脚平均位置调整身体高度和倾斜。

步态：

- 两足：左右交替。
- 四足：对角腿交替。
- 六足：三足支撑步态。

### 验收标准

- 生物能经过星球顶部、侧面、赤道和下半球。
- 足端始终落在地面，不会向世界 Y 方向悬空。
- 生物不会向星球 X/Z 坐标零点异常滑动。

## 11. 阶段八：星球表面生成系统

`PlanetCreatureSystem` 负责：

- 接收当前 `GalaxyPlanetDefinition`。
- 生成或读取固化物种。
- 查找合法表面位置。
- 创建和回收运行时个体。
- 管理人口和个体状态。
- 在星球保存时输出生物存档。

生成位置需要检查：

- 地面坡度。
- 是否在水下。
- 是否位于洞穴。
- 是否接近玩家出生点。
- 是否与建筑或资源重叠。
- 是否符合该物种生态区域。
- 是否满足同类群体间距。

建议分布：

- 群居食草生物每组 3 到 6 只。
- 捕食者单独或两只出现。
- 大型生物数量少、间距大。
- 小型生物数量多、活动范围小。

可以参考现有 `VoxelQuadSphereWorld.SpawnHarvestableResources` 的确定性表面放置和快照恢复流程，但生物需要额外处理活动区域、群体和运行时回收。

### 验收标准

- 每颗星球稳定生成三个物种。
- 出生点、建筑内部、水下和过陡表面不会生成陆地生物。
- 返回星球后物种定义不改变。

## 12. 阶段九：基础 AI

第一版状态机：

```text
Idle
  -> Wander
      -> Feed
      -> Flee
      -> Chase
```

性能要求：

- 感知每 0.2 到 0.5 秒更新一次。
- 使用 `Physics.OverlapSphereNonAlloc` 等无分配查询。
- 限制每次感知的最大目标数。
- 远距离生物停止完整 AI。
- 移动方向始终投影到当前球面切平面。

### 验收标准

- 食草生物会闲逛和逃离危险。
- 捕食者会追逐目标。
- AI 不依赖世界 X/Z 平面。
- Profiler 中没有每帧明显 GC 分配。

## 13. 阶段十：存档接入

在 `GalaxyPlanetSaveData` 中增加：

```csharp
public GalaxyCreatureSaveData creatureData;
```

建议结构：

```csharp
[Serializable]
public sealed class GalaxyCreatureSaveData
{
    public int generatorVersion;
    public CreatureSpeciesDefinition[] species;
    public CreatureInstanceState[] importantInstances;
}
```

必须保存：

- 已固化物种定义。
- 死亡个体。
- 驯服、命名或任务相关个体。
- 玩家明显影响过的种群状态。
- 特殊个体的位置、年龄和生命值。

不需要保存：

- 普通生物每一帧的位置。
- 运行时骨骼 Transform。
- Mesh 顶点。
- Material 实例。
- IK 和动画瞬时状态。

普通个体可以根据物种种子和种群状态重新生成。Mesh 根据已保存基因重建并缓存。

实施时将当前星球存档版本从 9 升级到 10。旧存档缺少生物数据时，在首次进入星球时生成并固化物种。

### 验收标准

- 杀死或驯服的重要个体不会在重新进入后重置。
- 物种外观、行为参数和名称保持不变。
- 不同存档之间不会串用物种数据。

## 14. 阶段十一：LOD、对象池和性能

推荐三级模拟：

```text
0 到 40 米：完整 Mesh、动画、碰撞和 AI
40 到 120 米：低模 Mesh、简化动画和低频 AI
120 米以外：不创建 GameObject，只保留数学种群状态
```

初始限制：

- 同时完整模拟不超过 20 只。
- 同时可见不超过 50 只。
- 同一物种只生成一次 Mesh 和共享材质。
- 使用对象池复用运行时个体。
- Collider 使用球体或胶囊体。
- 禁止给活动生物使用动态 MeshCollider。
- 每帧限制足部 IK 求解数量。
- 程序化网格数据可在后台计算，但 Unity Mesh 赋值必须回到主线程。

### 验收标准

- 生物离开范围后对象数量不会持续增长。
- 长时间游玩不会持续增加 Mesh 和 Material 数量。
- 天气、水体、资源和生物同时运行时帧时间保持稳定。

## 15. 后续高级能力

基础版本稳定后再依次增加：

1. SDF/Metaball 连续身体。
2. 通用动作语义与动画重定向。
3. 飞行生物。
4. 水生生物。
5. 爬行和无足运动。
6. 遗传、繁殖和微小变异。
7. 捕食关系和食物链。
8. 玩家生物编辑器。

飞行、游泳和无足运动应作为不同的 `CreatureLocomotion` 求解器，不应继续强行复用足部行走代码。

## 17. 开发原则

- 先生成稳定身体拓扑，再生成 Mesh。
- 先完成固定四足形态，再开放任意形态。
- 先实现程序化步态，再实现通用动作重定向。
- 所有随机结果必须来自稳定种子。
- 已访问星球的物种定义必须固化。
- 球面方向全部使用星球中心计算，禁止依赖世界 Y 轴。
- 运行时生物可以生成，但固定管理器必须手动挂在场景层级。
- 不保存可由基因重新构建的 Mesh、骨架和材质。
- 随机参数必须经过生物结构和星球生态约束。

最重要的实施顺序：

```text
数据模型
-> 稳定物种种子
-> 身体拓扑
-> Mesh
-> 骨架蒙皮
-> 球面步态
-> 表面生成
-> AI
-> 存档
-> LOD
-> 高级形态
```

如果跳过这个顺序，同时开发随机 Mesh、任意骨架、IK、球面移动和 AI，会难以判断问题来自模型拓扑、蒙皮权重、动画求解还是球面方向计算。
